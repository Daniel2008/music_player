# Windows 性能测量：2026-10-23

## 结论

当前源码在本机的主要性能压力位于 Flutter 栅格阶段，而非 Dart 界面构建阶段。播放页八种频谱的栅格 P95 为 34.47–38.35ms，全屏霓虹柱为 39.93ms；隐藏频谱时为 2.87ms。30 FPS 对应约 33.33ms 的单帧预算，因此部分频谱帧已超过这个预算。

这说明应该继续定位绘制、合成和呈现等待，不能仅凭这些数据断言某个 shader 或 GPU 已饱和。把霓虹柱配置从 30 改为 60 FPS，本轮没有观察到整体 Flutter 帧吞吐增加。此次只测量，没有实施性能修复。

## 条件与方法

- 时间：2026-10-23 18:39–18:44，Asia/Shanghai。
- CPU：Intel Core Ultra 9 275HX，24 核 / 24 逻辑处理器；约 32GiB 物理内存。
- 系统：Windows 11 专业版，10.0.26300；Flutter 3.47.1 / Dart 3.13.1。
- 模式：当前未提交工作区源码的 Windows **Profile** 构建，入口 `tool/performance_probe.dart`。不是旧 Release 包，也不是 Debug 模式。
- 使用生产 `main`、`AppRoot`、音频引擎、SMTC、播放页、歌词和页面导航；没有用假播放器代替原生音频。通过组件公开回调自动切换场景，没有测量鼠标/键盘输入延迟。
- 隔离 SharedPreferences 与结构化存储，测试文件均位于 `build/verification/performance/fixture`；用户收藏、历史、播放列表和设置未参与测试。
- 固定数据：500 首队列条目指向同一个 600 秒 PCM16 单声道 44.1kHz WAV；多频率测试信号带周期包络，音量 8%；同目录同步歌词每 2 秒一行。音频提前在另一个进程生成，排除生成时约 50MiB 缓冲区对被测进程内存的影响。
- 普通窗口：1904×1191 物理像素；全屏：2560×1600；DPR 1.5。未修改系统 DPI。
- 每个场景预热 3 秒，常规采样 12–15 秒；瀑布谱追加 60 秒连续采样。共 16 个场景，固定执行顺序，仅一次完整运行。
- CPU/内存每约 1 秒采样；GPU 使用 Windows 按 PID 过滤的性能计数器。CPU/GPU 汇总去掉每段首尾各一个样本，以减少切换边界混入。
- CPU 表示全机 24 逻辑处理器归一化占用；单核等效占用见 `summary.json`。例如瀑布谱 2.08% 全机，等效约 49.93% 单核，不是占满两个核心。
- GPU 列为该进程最忙引擎的平均忙碌率，不是整机总 GPU 利用率。枚举到 NVIDIA、Intel 和虚拟显示适配器，本轮没有将计数器 LUID 映射到具体适配器，不能宣称正在使用 NVIDIA 独显。
- GPU 采样从粒子阶段附近接入，前几个场景没有 GPU 数据，表内用“未采”标明。
- 期间使用少量窗口快照确认真实窗口及动态频谱，未持续录屏。结果会受本机其他应用、驱动和显示环境影响。

### 如何解读

1. **栅格阶段是下一步优先定位方向。** 八种样式的构建 P95 最高约 2.6ms，栅格 P95 却普遍超过 33.33ms。先做同场景绘制/合成 trace 和受控 A/B，区分频谱绘制、场景合成、显示呈现等待；不要先全面重构 Provider。
2. **60 FPS 暂无收益证据。** 霓虹柱 30/60 配置下，采集到的整应用 Flutter 帧吞吐约 38.66 / 37.93 帧每秒。这个计数包括时间轴、歌词等重绘，并非频谱自身的刷新率，也不是屏幕实际呈现帧率。一次顺序对比不足以证明 60 FPS 一定更差，但不支持把它设为默认。
3. **瀑布谱是 CPU 侧重点。** 连续段约 2.08% 全机 / 49.93% 单核等效，波浪约 1.22% / 29.26%。后续应在相同队列、分辨率、输入下复测历史谱栅格化成本。
4. **暂停能够停绘。** 暂停段 GPU 忙碌率归零，没有观测到持续动画空转；停止后平均 0.15%，有少量偶发更新。隐藏频谱时仍有时间轴约 10Hz 更新，这是独立场景的结果。
5. **内存需分层确认。** 全部 OS 样本中，工作集峰值 1332.4MiB（约 1.30GiB），位于全屏阶段。停止后平均工作集 911.5MiB，GPU 共享内存约 598.8MiB；这些指标可能重叠，不能相加。固定执行顺序使后期场景包含前面已暖起来的资源缓存，不能把样式间 RSS 差值当作单个样式的独立成本。
6. **不能确认或排除泄漏。** 60 秒瀑布谱段首/尾各 8 个 CPU 样本的平均工作集由 911.0 增至 925.2MiB，私有提交由 881.6 增至 893.0MiB，句柄平均由 766.8 降至 757。共享显存没有持续单向增长。需要更长时间、重复进入退出相同场景，并结合 Dart 堆、原生资源和 GPU 分配记录才能归因。

原始字段 `frames_over_16_67ms` 只是超过 60Hz 单帧耗时阈值的计数，**不等于掉帧数量**，也不能用于声称 30 FPS 配置的卡顿率。

## 验证与未覆盖项

- Profile Windows 构建成功；项目 `dart analyze` 无问题；PowerShell 脚本语法检查通过。
- 16 个场景的数据完整性检查通过，每段时长不少于 10 秒、CPU 样本不少于 8 条；304 条进程样本、211 条 GPU 样本；记录到的 Flutter 异常为 0。
- 未测真实歌曲解码差异、在线缓冲和下载、启动耗时、弱显卡、电池模式、其他 DPI、多平台，以及 30–60 分钟资源趋势。
- 本轮不是 Release 发行包验收，也未实施任何性能优化；现有业务代码未更改。

## 复现

1. 在项目根目录构建隔离入口（Profile）：

   ```powershell
   $env:PATH = 'C:\Windows\System32\WindowsPowerShell\v1.0;C:\Windows\System32;D:\worksoft\.cargo\bin;' + $env:PATH
   $env:CARGO_HOME = 'D:\worksoft\.cargo'
   flutter build windows --profile --no-pub --target tool/performance_probe.dart
   ```

2. 启动 `build/windows/x64/runner/Profile/music_player.exe`。确认 `build/verification/performance/phase.json` 中的 PID 为本次进程，并已进入新的 `warmup_...` 阶段；再在两个终端分别执行：

   ```powershell
   ./tool/measure_process.ps1
   ./tool/measure_process.ps1 -GpuOnly
   ```

3. 入口自动切换场景并在结束后停止音频。`phase.json` 为 `done` 后采样器结束；关闭该隔离窗口即可。复测前先归档上一轮输出；结果默认覆盖同一目录。
4. 本机首次构建曾因命令 PATH 缺少 Windows PowerShell 导致 Cargokit 生成 `/run_build_tool.cmd`。仅修正当次 PATH 并重新执行 CMake 配置即恢复，没有修改插件源码。该环境问题与运行时性能结果分开记录。
